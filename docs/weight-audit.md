# 轻量化重估 — 砍掉不必要的重量

> 前提决策（已定）：不做锁屏诗、不做会议内容理解、不做邮件正文读取、不做自动操作其他应用；
> 不接本地小模型，改接 API；插件式，一切可自定义。

---

## 一、"接 API 代替本地小模型"砍掉的重量

这一条远比看起来重要。它一次砍掉四样东西：

| 砍掉                      | 重量                                |
| ------------------------- | ----------------------------------- |
| Ollama / llama.cpp 运行时 | 数百 MB 依赖 + 模型文件（1–8GB）    |
| 模型生命周期管理          | 下载、更新、显存/内存检测、模型切换 |
| GPU/驱动兼容矩阵          | 各厂商推理后端差异                  |
| 首字延迟硬伤              | 本地 3B 在 CPU 上只有 5–15 tok/s    |

**净效果：安装包从 GB 级降到 100MB 级，"点它 → 出话"的延迟从不可控变成可控。**

但接 API 引入了三个新重量，必须一并设计掉，否则会以更隐蔽的方式变重：

1. **密钥管理。** API Key 绝不能明文写进配置文件。用系统密钥链（Windows Credential Manager / macOS Keychain），配置里只存引用。
2. **成本与限流。** 必须有每日 token 预算、本地结果缓存、失败重试上限。否则一个爱说话的桌宠会悄悄烧钱，用户收到账单就卸载。
3. **降级路径。** API 挂了/超时（>2s）/超预算，必须自动回落模板句。**模板层不是省钱的补丁，是架构的必选层**——桌宠的气泡必须秒回，90% 的表达靠模板，API 只负责"值得等一下"的 10%。

## 二、还有哪些"重"的地方 —— 按严重度排序

### 🔴 #1 向量检索 / 嵌入模型（建议直接砍掉）

你原方案写 `SQLite + sqlite-vec / LanceDB`。对一个本地桌宠来说这是**杀鸡用牛刀**：

- 要么接嵌入 API（每次写入记忆都要一次网络往返，成本和延迟双增）
- 要么带一个本地嵌入模型（又把刚砍掉的模型依赖请回来了）

而桌宠的记忆规模是**千条量级**，SQLite FTS5 全文检索 + 时间/情绪/标签过滤完全够用，甚至比向量检索**更可控**——用户能看懂"它为什么想起这件事"。

> **决策：SQLite + FTS5，不引入任何向量库。** 这是一个纯减法，能力不降。

> **⚠️ 2026-09-12 更正（M3 施工后）**：本文的**主结论不变**——
> 砍掉向量库是对的，SQLite 够用。但"用 **FTS5**"这个**手段**在本机做不到
> 中文子串检索（实测 `MATCH '加班'` → 0/5，两种分词器都漏 2 字词），
> 实际实现改用 `LIKE '%词%'`。**注意这不影响本文的减重账**：
> LIKE 是 SQLite 自带能力，依赖数**同样是 0**，`-1 依赖` 那一行依然成立。
> 详见 `docs/verify-m3-fts5.md` 与 `docs/DECISIONS.md`。

### 🔴 #2 任意代码插件沙箱 + 技能市场（建议分期，v0.1 不做）

"插件式"和"插件市场"是两件事。市场需要沙箱隔离、签名校验、审核流程、版本兼容、崩溃隔离——**这是第二重的模块**。

轻量做法：

- **v0.1 只定接口**：插件 = 一个 manifest（声明触发条件/感知需求/配置项）+ 一组钩子函数。内置技能就用同一套接口写，**自己先当第一个插件作者**。
- 插件在主进程内运行，不做沙箱（明示风险，仅支持可信来源）。
- **v0.3 再考虑** WASM/受限沙箱与分发市场。

> 关键：接口必须在 v0.1 就定好，否则 v0.3 是一次重写而不是一次扩展。**定接口 ≠ 建市场。**

### 🟠 #3 Live2D（建议降级为"可选的表达后端"）

Live2D 重在三处：运行时体积、**许可门槛（与业务规模挂钩，商业发布前必须自行确认官方条款）**、以及**美术资源成本**——小团队真正卡住的是最后一项，没有画师就没有 Live2D 模型。

轻量做法：**v0.1 用精灵图（sprite sheet）**，把宠物形象定义成"帧序列 + 状态映射"的用户可替换资源包。用户想自定义形象，丢一个文件夹进去就行。

好处：零许可风险、零运行时依赖、美术门槛降到"会用任何绘图工具"。Live2D 作为 v0.3 的可选后端插件接入（参考开源桌宠项目的既有实现）。

### 🟠 #4 表达通道过多（建议设上限）

你列了 5 条通道（动画/气泡/音效/桌面物件/系统通知）+ 8 种形态。单条都轻，**同时存在就重**：渲染压力、资源体积、以及**注意力互相竞争**。

轻量做法：同时活跃的表达通道 ≤ 2（通常是"动画 + 气泡"）；桌面物件是插件而非核心；形态切换用同一套精灵的不同状态实现，不做 8 套独立资源。

### 🟡 #5 跨平台（建议 v0.1 只做 Windows）

Windows / macOS 在透明窗、托盘、权限模型、开机自启上差异巨大。同时做两个平台 = 两倍验证成本。轻量做法：**平台层抽好接口，但只实现 Windows**，macOS 留到 v0.5。

（本机是 Windows，且当前只有 Node + git，见下节。）

### 🟡 #6 社交层（建议整层延后）

mDNS 在企业 WiFi 基本必挂（多播阻断 + 客户端隔离是标准安全配置），且它是唯一需要**额外服务器**的模块。轻量做法：v0.1 **整层不做**；v0.2 只做"手动 IP 配对"；mDNS 作为可选插件。

### 🟡 #7 代码签名与自动更新（建议 v0.1 明确不做）

代码签名证书是**年费**，且透明置顶的常驻应用积累信誉很慢，没签名会被 SmartScreen 挡。这不是技术问题而是成本问题——**要清醒地接受"首版安装转化率会有损失"**，别在 v0.1 试图解决它。

## 四、本机工具链现状（决定第一步能不能跑起来）

实测：

```
git      OK   D:\tools\Git\cmd\git.exe
node     OK   D:\tools\nodejs\node.exe        (v24.15.0)
npm      OK   D:\tools\nodejs\npm.ps1
python   OK   D:\tools\Python314\python.exe
rg       MISSING     pnpm  MISSING    yarn   MISSING
cargo    MISSING     rustc MISSING    gh     MISSING
```

**这个结果直接决定技术栈选择**：

- **🟢 Electron：今天就能动工。**只需 npm，零安装。透明窗 + 点击穿透（`setIgnoreMouseEvents`）生态最成熟，而这正是 v0.1 最大的技术风险点。代价是安装包 80–150MB。
- **🔴 Tauri：要先装 Rust 工具链 + MSVC Build Tools（数 GB、需重启终端），然后还要趟 WebView2 的透明/每像素 alpha 坑。**代价是首日大概率卡在环境上。

> **建议：v0.1 用 Electron，换"首日能跑通透明穿透"。**理由是这个项目的头号风险是透明置顶窗，而 Electron 在这方面最不需要试错。等 v0.3 产品形态稳定、且已验证 Tauri 的透明表现后，再评估是否迁移（此时插件接口已定好，迁移成本可控）。
>
> 若你坚持 Tauri，prompt 里已把这条做成参数，改一处即可。
