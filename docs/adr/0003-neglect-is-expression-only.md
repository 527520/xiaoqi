# 被冷落是纯表达状态：无条件回应

**Status**: accepted（2026-09-11）

## 背景

产品要允许宠物因"被冷落"而产生行为表达（背对用户、偷看、开场白带委屈），这样"它记得"才可见、它是一个有内在状态的角色。但产品的三大红线之一是**不道德绑架**——永不使用内疚感驱动互动。

这两者之间存在真实的冲突：**"生气"最自然的实现方式，就是惩罚用户**（不理他、要他哄、降低回应意愿）。而只要惩罚机制存在，宠物就会从"室友"变成"需要维护的关系负担"——这正是本产品要避免的东西。

同时，"被冷落"的推断依据必须来自我们允许的感知信号，而这些信号**无法区分"用户很忙"和"用户故意冷落"**。这个不确定性必须由设计吸收，而不是由更激进的感知来弥补。

## 决策

1. **被冷落是纯表达状态。** 它只改变宠物如何表现自己（姿态、开场白、语气），**永不改变它是否愿意回应**。
2. **无条件回应。** 用户一旦发起互动，宠物必须立即回应并自行给出台阶，**用户不需要道歉、补偿或"哄"**。
3. **禁止的形态**：拒绝互动、需要补偿才理你、情绪强度跨天累积成怨气、把冷落归因于用户的品格（"你是不是不爱我了"）。
4. **误判吸收**：若用户长时间在别的应用里高强度活动（如游戏、看视频、赶工），一律**不推断为冷落**——宁可让宠物不表现委屈，也不要冤枉用户。这条把"无法区分"的代价放在宠物一侧，而不是用户一侧。
5. **情绪上限 3 件、每日重置基线**，且任意正向互动可清零。

## 后果

- 状态机需要显式的"用户意图不明确"分支，并在该分支下**默认选择不表现负面**。这是一个刻意的不对称：误判为"没被冷落"只是少了一点趣味，误判为"被冷落"会让用户内疚。
- 文案层的测试不能只测"说了什么"，还要测"**用户伸手之后它是否立刻靠近**"——这是可自动化的状态机断言。
- "记仇"这个说法在本产品内**不再使用**（见 CONTEXT.md 的 `_Avoid_`）；正确用词是**被冷落**。用词会塑造实现者的直觉。

## 被否决的方案

- **不做任何负面记忆，只留好感度**：最安全，但宠物对"被冷落"毫无反应，会显得没有内在状态，"记忆是灵魂"失去可见证据。
- **完整的情绪惩罚（不理用户、需要哄）**：最常见的拟人化做法，也是最容易翻车的做法。这里是本产品与"养成游戏"的分界线——养成游戏用愧疚感换留存，本产品明确不换。
