# 感知授权按进程分级，不按数据类型分级

**Status**: accepted（2026-09-11）

## 背景

桌宠需要"知道用户在什么场景"才能切换形态与语气。常规做法是把感知项按隐私风险分级（时间/应用名/窗口标题/屏幕内容/摄像头各为一级），然后逐级授权。

开发期实测发现这个模型在本产品上是错的：在同一台机器上读取前台窗口标题，得到的是

```
msedge :: 升级 PowerShell 并安装 rg — DeepSeek Harness 和另外 5 个页面 - 个人 - Microsoft Edge
```

也就是说，**"窗口标题"这一项的风险完全由前台是什么应用决定**——前台是 IDE 时它几乎无风险，前台是浏览器、密码管理器、银行页面或隐私窗口时，它等于在读正文摘要。把它归为"低风险、默认开"的一级，会让产品在用户毫无察觉的情况下获得内容级信息。

## 决策

1. **按进程授权，不按数据类型授权。** 前台**进程名**默认开启（它确实低风险）；**窗口标题**默认仅对白名单进程开启（IDE、终端、会议客户端、邮件客户端），浏览器与密码管理器默认关闭。
2. **v0.1 完全不读窗口标题。** 工作模式的推断只靠三项信号：前台进程名、系统空闲时长、系统级状态。
3. 需要新增敏感度时，**新增一个进程白名单项，而不是新增一个"数据类型"级别**。

## 后果

- 感知层的代码形状是"进程名 → 场景标签"的映射表，不是"级别 → 开关"的阶梯。用户看到的是"它认得 VS Code"，不是"已授权 L1 权限"。
- 场景推断的准确率上限因此更低，且**这是刻意接受的代价**——用可解释的"认得几个应用"换取永不触碰内容。
- 若将来确需窗口标题（例如区分浏览器里的不同 Web 应用），必须走"具体进程 + 用户显式逐个添加"的路径，且默认空列表。

## 被否决的方案

按数据类型分级（原设计方案）。否决理由不是隐私洁癖，而是该模型会**系统性地低估**某一级的真实风险上限：一个级别的风险取决于最坏的那个应用，而不是平均值。
