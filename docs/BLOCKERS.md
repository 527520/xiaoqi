### 规格怎么说的

> 中文分词：FTS5 默认 `unicode61` 对中文按字切分，子串检索可用

### 实测是什么

原样复刻 V1 那个用例（`node scripts/recheck-v1-fts5.mjs`）：

```
MATCH '加班'                     → 0 条    ← V1 声称这里有 1 条
MATCH '加' / '昨天' / '也在加班'   → 均 0 条
MATCH '用户昨天也在加班'           → 1 条    ← 用**整句**查才命中
```

**根因**（用 `fts5vocab` 直接读 token，不靠推断）：

```
"用户昨天也在加班"  → 1 个 token: ["用户昨天也在加班"]
"用户 昨天 加班"    → 3 个 token: ["加班","昨天","用户"]
"用户，昨天：加班"   → 3 个 token: ["加班","昨天","用户"]
```

`unicode61` **按"词"切分，不是按"字"切分**。中文没有词间空格，
所以一整句连续中文 = **一个 token**；而空格与中文标点**是**分隔符，
有分隔时切分就正常。V1 当时很可能验的是"原句能查到原句"。

换 trigram 也不行（`node scripts/probe-fts5-strategy.mjs`）：

```
A. 默认 FTS5（unicode61）      命中 0/5
B. trigram FTS5                命中 0/5
C. trigram + 短查询 LIKE 兜底   命中 5/5   ← 靠的其实是 LIKE
D. 纯 LIKE（对照）             命中 5/5
```

（脚本输出写的是 `/7`，因为词表里 `开会`、`摸鱼` **本来就不在测试数据里**。）

### 第二轮查证补充的硬依据

| 查证项                | 结果                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| trigram 为何漏 2 字词 | `MATCH` 把**查询串也按同一分词器切**；"加班"切成 1 个 token，而正文 token 都是 3 字的 → 无交集                                 |
| 前缀查询能否救        | **不能**。前缀只匹配 token 开头：`MATCH '加班*'` → 0，`MATCH '用户*'` → 1。句中词永远命不中                                    |
| ICU 分词器            | **不可用**（这份 SQLite 未编译 ICU；`no such tokenizer: icu`）                                                                 |
| 自写分词器            | 社区标准解法，但是**原生扩展**——本机无 C++ 编译器，装不了也编不了                                                              |
| LIKE 大小写           | 默认**不敏感**；中文无大小写，开关都不影响语义                                                                                 |
| LIKE 性能             | 5,000 条 **0.240ms**／20,000 条 **0.917ms** 单次全表扫描                                                                       |
| 建索引能否加速子串    | **不能**。`EXPLAIN QUERY PLAN` 显示子串恒为 `SCAN`；只有**前缀**在 `case_sensitive_like=ON` 时才走 `SEARCH ... COVERING INDEX` |

### 为什么这是"自相矛盾"而不是"我该自己决定"

规格给的**理由**（千条级够用、不引向量库、可解释）**成立且我完全同意**；
规格给的**方案**（FTS5）在本机**恰恰实现不了它要的检索**。
而且这不是版本问题——是 FTS5 分词模型与中文书写方式的结构性错配，
换机器也一样（除非编一个原生分词器）。

另外它踩到 §1.2⑪「删掉的记忆必须真的消失」（不同方案对删除留痕处理不同）。
「不引入向量库」这条我**不会**违反，下面三个选项都不涉及向量库。

### 三个选项

| 选项            | 做法                                                               | 代价                                                                                       |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **A（我推荐）** | 检索用 `LIKE '%词%'` + `case_sensitive_like=ON`；**不建 FTS 表**   | 全表扫描，但**千条级 ≈ 0.05ms**（实测外推），完全无感。字面上偏离了"用 FTS5"               |
| B               | 保留 FTS5 表但只当"整句/长片段"索引用；检索主路径仍走 LIKE         | 多一张表 + 一套触发器要维护同步，实际收益为零（0/5 命不中）                                |
| C               | 自写 bigram 分词：写入时把中文切成 2 字滑窗存进 FTS 表，查询同样切 | 能用上 FTS5，但**要自己维护分词与查询改写**，代码量与出错面明显变大；收益只是"用上了 FTS5" |

我建议 **A**：它满足规格的**理由**，只是不用达不到目的的那个**手段**。
若你更看重"照字面执行规格"，选 C 我可以实现，但会在
`docs/DECISIONS.md` 写明它为什么更复杂而收益更小。
