# 记忆内容层（阶段二）—— 验证证据

**范围**：核心记忆块（常驻上下文）、事实巩固（new/reinforce/supersede/discard）、
双时间字段（被取代而非软删除）、账本界面上的可见与可改。

**不在范围内**：向量检索与 LLM 抽取层（需要密钥，后置）。

---

## 1 · 这一层解决什么问题

检索式记忆有个结构性缺陷：**重要的事会被漏掉**。
"用户不喝咖啡"如果某次检索没命中，宠物就会推荐咖啡——
而这恰恰是最伤信任的一类错误。

四层记忆各管一件事：

| 层         | 进上下文的方式     | 上限           | 谁管             |
| ---------- | ------------------ | -------------- | ---------------- |
| **核心块** | **永远进**         | 每块有字符上限 | 用户可编辑       |
| 情景记忆   | 按时间衰减 + 检索  | 遗忘曲线       | `model.ts`       |
| 语义记忆   | 按检索命中         | —              | `consolidate.ts` |
| 情感记忆   | 按时间衰减（最慢） | 遗忘曲线       | `model.ts`       |

## 2 · ★ 这一轮修掉的一个真 bug：被取代的旧事实仍在参与回应

### 症状

`superseded_by` 是双时间字段，让"新事实推翻旧事实"时旧条**留在库里当历史**。
但 `MemoryStore.search()` **没有任何地方按它过滤** —— 也就是说：

```
memory.db 里：
  id=1  "用户喝咖啡"      superseded_by=2
  id=2  "用户不喝咖啡"    superseded_by=NULL

composeContextForPrompt() 检索到的：
  两条都进 → prompt 里同时出现「用户喝咖啡」与「用户不喝咖啡」
```

两条**互相矛盾**的事实同时进上下文，模型只能按先到的那条答 ——
也就是有一半概率用错。而这属于最难被察觉的一类错误：
不报错、不崩溃，只是偶尔说反话。

### 修法

`SearchOptions.superseded` 三态，**默认 `'live'`**：

| 取值             | 含义           | 谁用                        |
| ---------------- | -------------- | --------------------------- |
| `'live'`（默认） | 只给当前有效的 | 检索、拼 prompt、账本主列表 |
| `'only'`         | 只给被取代的   | 账本的"历史"视图            |
| `'all'`          | 全给           | 诊断                        |

默认取安全侧是刻意的：**把历史显式打开，比把"忘了排除"变成一次静默的错误召回要难得多。**

### 反向验证（证明这条断言真的能失败）

把过滤临时移除，重跑测试：

```
$ pnpm vitest run src/main/memory
 ❯ src/main/memory/service.test.ts (29 tests | 1 failed)
     × ★ 同主题矛盾 → supersede：新旧都在，旧的被标记为被取代
   AssertionError: expected [ …(2) ] to have a length of 1 but got 2
```

还原后 29/29 通过。**"默认检索只有新的那条"这条断言确实能失败**。

## 3 · ★ 第二个真问题：升级路径漏传了来源（provenance）

`#applyPromotion` 从"直接 `addSemantic`"改成走 `consolidateFact` 时，
一开始漏传了 `plan.derivedFrom`。而 `addSemantic` 的 `derivedFrom` 是**可选**参数
—— 不传也能跑，只是账本从此只能显示一句**没有来由的结论**，
用户无法判断该不该信（业内的说法是 provenance 丢失）。

可选参数漏传不会报错，所以只能靠断言钉住。反向验证：

```
移除 derivedFrom 传参后：
     × ★ 同类事件攒够次数后升级，且被吸收的情景记忆真的被删掉
   AssertionError: expected undefined to be defined
```

## 4 · 为什么升级要改走巩固决策

初版的升级路径是"直接写入"，而 `planPromotions` 只看**主题键**
"这个主题有没有语义记忆"，**不看既有事实的内容**。于是：

- 同一件事被反复凝练时，会攒出好几条几乎一样的事实，各占一行、同时进 prompt；
- "用户喝咖啡" → "用户戒咖啡了"这种**真矛盾**没有任何处理路径。

`consolidateFact` 的四选一决策正好补上这一段：

| 决策        | 落地动作                                                 |
| ----------- | -------------------------------------------------------- |
| `new`       | 写入（带上 `derivedFrom`）                               |
| `reinforce` | **不新增**，把既有那条的权重按 `reinforcedWeight` 提上去 |
| `supersede` | 写入新条 + 把旧条标为被取代（**不删**）                  |
| `discard`   | 什么都不做                                               |

### ★ 吸收掉的情景记忆要**无条件**删，与决策无关

`planPromotions` 的 `coveredTopics` 门挡住"已有同主题就不要重复升级"，
所以走到落库时该主题**从来没有**过语义事实 —— 决策只可能是 `new`。

但关键在于：**这些情景记忆已经被这条事实吸收了**。它们不能留在库里，
否则同一条证据会在下一轮再次凑够阈值、再次尝试升级，无限循环。
**事实写没写成，不该决定证据留不留。**

| 组件       | 失效方式                                                 | 单测能发现吗        |
| ---------- | -------------------------------------------------------- | ------------------- |

## 7 · 界面上刻意做的两个决定

### 7.1 核心块**可编辑**，不是只读展示

核心块每一轮都进 prompt，不参与相似度竞争。一条说错了的常驻事实
比一百条检索式记忆更伤 —— 它会持续影响宠物对用户的**每一句话**。
所以用户必须能看见它、改写它、清掉它。

### 7.2 每块显示"还能写多少"

上限直接决定常驻内容吃掉多少 token。上限**只在主进程有一份真相**
（`BLOCK_LIMITS`，随视图一起送出来），界面不复制 ——
复制的那份会漂移，而漂移的表现是"界面说还能写、实际被裁掉了"，
用户完全无法理解。

顺带一个纪律：`human` / `now` 空着就是**真的空**，不给它们编造内容。
`persona` 有默认内容是因为"它自己是谁"必须有起始语气；
而给 `human` 编内容就等于**它记得一些你没说过的事** —— 那是个很糟的错觉。

## 8 · 尚未验证的部分（诚实清单）

- **LLM 抽取层**：`composeContextForPrompt` 的输出目前只显示在账本里，
  **没有真的送给模型**（需要 API key）。所以"这段上下文能否让模型
  表现更好"这件事没有被验证过 —— 验证过的是**它被正确拼出来了**。
- **向量检索**：`sqlite-vec` 0.1.9 已实测可加载、KNN 可用，
  但没有接进这一层。
- **`supersede` 的真实触发**：端到端脚本里那条被取代的事实是
  **直接写库预置**的，不是由巩固决策产生的（界面上做不出这条路径）。
  巩固决策本身有单测覆盖，但"用户实际使用中会自然产生取代链条"
  这件事没有在真机长跑里观察到。
- **账本窗口在多显示器/混合 DPI 下的整页截图**：只在当前显示器上截过。
- 核心块**字符上限**对模型行为的影响没有量化（没有 key，测不了）。
