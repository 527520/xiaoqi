# 精灵图后端（图集宠物）—— 验证证据与已知限制

本文记录**第二条渲染后端**：把用户提供的 Codex 桌宠图集当作宠物形象。

程序化后端（矢量画的小奇）没有消失，它仍是默认值。两条后端并存，
由 `XIAOQI_PET_DIR` 选择。

---

## 1 · 它解决什么问题，代价是什么

### 解决的

用户对程序化形象的评价是「你画的还是太丑了，我想要的是如图那样的」。
程序化矢量画法在这台机器上已经调到极限（迭代了 5 版解剖 + 3 版光照），
仍然达不到参考图里那种手绘质感。而 Codex 桌宠社区已经积累了**大量**
画好的图集（`legeling/awesome-codex-pet` 收录 239 只）。

所以这一版把"画宠物"换成"**加载别人画好的宠物**"。

### 代价（必须说清楚，不藏）

| 能力             | 程序化后端                 | 精灵图后端                 |
| ---------------- | -------------------------- | -------------------------- |
| 情绪表达         | **8 种**（施工令 §4.6）    | **最多 4 种**（见下表）    |
| 眨眼 / 呼吸      | 有                         | 素材自带，宿主无法控制     |
| 瞳孔跟随光标     | 有（连续偏移）             | 只有 16 个离散方向格（V2） |
| 关系基调影响幅度 | 有（呼吸深浅、摇摆、前倾） | 只有反应灵敏度             |
| 外观上限         | 我们画功的上限             | **素材画功的上限**         |

**这是一次交易，不是升级。** 想要完整 8 情绪时，程序化后端仍然在。

## 2 · 情绪 → 动作的对照表（含"为什么回落"）

图集的 9 个动作与我们的 8 种情绪**不是一一对应的**。硬凑会得到一堆
牵强的映射，所以能对应的如实对应，对不上的**明确回落 `idle`**
并把理由写进表里（`src/renderer/src/pet/spriteAnimation.ts`）：

| 情绪        | 动作      | 理由                                                |
| ----------- | --------- | --------------------------------------------------- |
| `happy`     | `waving`  | 高兴 → 挥手                                         |
| `surprised` | `jumping` | 惊讶 → 跳起来                                       |
| `aggrieved` | `failed`  | 委屈 → 垂头丧气                                     |
| `close`     | `waving`  | 亲近 → 挥手                                         |
| `calm`      | `idle`    | 平静本来就是 idle                                   |
| `focused`   | `idle`    | **图集没有"专注"**；`review` 是"检视文档"，语义不同 |
| `sleepy`    | `idle`    | **图集没有"困"**；`waiting` 是"等用户"，硬用会误导  |
| `bored`     | `idle`    | **图集没有"无聊"**；`waiting` 表达期待而非无聊      |

工作模式（用户的处境）也有一张表，但它**只在情绪落到 idle 时才生效**——
否则"用户在开会"会盖掉"宠物很高兴"，那就本末倒置（情绪是宠物自己的状态）。

`overtime`（加班）映射到 `running`（陪着干活），**绝不**用 `failed`——
那等于在暗示"你加班好惨"，正是 ADR-0003 禁止的评判。

### 优先级（从高到低）

1. 隐身 → 不播
2. 静默 → `idle`
3. **交互回应** → `waving`
4. 等用户 → `waiting`
5. 检视 → `review`
6. 情绪
7. 工作模式
8. 兜底 `idle`

第 3 条排在情绪与工作模式**之前**是刻意的：ADR-0003 要求**无条件回应**
（"用户一伸手就必有反应"），不能因为"宠物正在忙"就不理人。

## 3 · 命中判定：为什么必须下采样成点阵

### 问题

穿透开关是**整窗**的（`setIgnoreMouseEvents`），而决定何时翻转的是
每 80ms 一次的光标轮询。轮询必须在**主进程**：光标一旦移出宠物轮廓，
鼠标事件就穿透出去，渲染进程根本收不到那些 move。

但图集在渲染进程里（Chromium 的解码器在那儿）。所以剪影必须传过去。

传整张图不行（1536×2288×4 ≈ 14MB）。所以渲染进程把 alpha **下采样**成点阵：

```
13 列 × 16 行，每点约 14.8×13 精灵像素
每行 4 个十六进制字符（16 位，用掉 13 位）
9 个动作 × 16 行 × 4 字符 ≈ 600 字节，一次 IPC
```

13×16 的来由：格子是 192×208，`192/13 ≈ 14.8`、`208/16 = 13` ——
**横向与纵向的点尺寸几乎相等**。差得远会让判定在某个方向系统性偏胖，
表现为"明明点在猫身上却穿透"。

### 点阵区域带偏移

一张 192×208 的格里，宠物通常只占中间一块。所以渲染进程按实际内容
算出**点阵区域**（`selectMaskGrid`），随蒙版一起传；主进程不重算，
只按同一套映射把光标坐标换算过来——于是编码端与解码端不可能用不同的网格。

### ★ 没有蒙版时一律穿透（安全侧）

蒙版要经过"解码 → 下采样 → IPC"才到主进程。在它到达之前的窗口期里：

- 默认判"可点" → 宠物**挡住下层窗口却点不动**。用户会以为应用卡死，
  那是直接卸载级别的故障。
- 默认判"穿透" → 只是"宠物暂时点不到"，而它本来只有几百毫秒。

取后者。`hitTestSpriteMask` 在 `mask` 为 `undefined` 时返回 `false`，
并且**有一个测试专门钉住它**。

### 已知取舍（不假装精确）

1. **按动作存蒙版，不按帧**。同一动作内各帧的剪影高度重合，所以取并集。
   代价："抬手那一帧的指尖点不到"。收益：数据量降一个数量级（51 张 → 9 张）。
2. **渲染进程侧的判定用的是当前动作，主进程可能滞后几十毫秒**
   （动作名 250ms 上报一次）。这个滞后是已知且可接受的。
3. 点尺寸约 14 像素，所以轮廓边缘有约一个点的判定误差（在 100% 缩放下 ≈ 14 DIP）。

## 4 · 验证证据

### 4.1 纯数据端到端：`pnpm verify:sprite` —— 40/40

从磁盘上的素材一路验到"哪个像素可点"：

```
① 元数据与图集文件头        5 项
② 像素解码与命中蒙版        5 项
③ 蒙版密度（两头都有反例）  4 项
④ 命中判定                  7 项
⑤ 缩放不变形                4 项
⑥ 切帧与时钟推进            7 项
⑦ 注视方向                  5 项
⑧ 程序化后端回归            2 项
```

**每条关键断言都配了反例**——"扫描没发现问题"本身没有价值，
要先证明这个扫描**能**发现问题：

| 正向断言                       | 配对的反例                                       |
| ------------------------------ | ------------------------------------------------ |
| 九个动作的占格扫描都数满       | 喂全透明像素时扫描应为 0 帧                      |
| 蒙版有点亮的点                 | 蒙版**不是**全亮（否则等于没有逐像素判定）       |
| 轮廓内的点路由到 `pet`         | 蒙版未点亮的点必须穿透（同窗口内，区别只在蒙版） |
| 蒙版为 null 时轮廓内的点也穿透 | ——（这条本身就是安全侧的反例）                   |
| V2 的版本校验通过              | 把 `spriteVersionNumber` 改成 1 后**必须**失败   |

### 4.2 实时点击穿透：`pnpm verify:sprite-live` —— 10/10

纯函数证明不了这四件事，它们只能真跑：

```
✅ 主进程打印了宠物形象署名
✅ ★ 蒙版经 IPC 到达主进程
   精灵图蒙版已接收（9 个动作；点阵区域 192×208 格内像素）
✅ 蒙版没有被拒收
✅ ★ 窗口尺寸是格子的比例（192×208 × 缩放），**不是**正方形
✅ 窗口宽度等于 V2 格宽（缩放 1）
✅ 窗口左上角（格内但轮廓外）        光标 (744,264) → passthrough
✅ ★ 蒙版点亮的点（轮廓内）          光标 (836,371) → pet
✅ ★ 蒙版未点亮的点（同窗口内，轮廓外） 光标 (792,280) → passthrough
✅ 回到轮廓内（可逆的翻转）          光标 (836,371) → pet
✅ 窗口外                            光标 (540,60)  → passthrough
```

探针点**从真实蒙版算出来**，不是我手填的坐标——这样探针与被测对象同源，
素材一换不会失效。

### 4.3 真实素材（`wangcai`，V1 8×9）—— 40/40 与 10/10

上面两节的数字都是拿**程序化测试图集**跑的。拿真实素材（一只坐姿布偶猫，
1536×1872，V1）重跑：

```
pnpm verify:sprite      <真实素材目录>    40/40
pnpm verify:sprite-live <真实素材目录>    10/10
```

它顺带暴露出**验证脚本自己的两个缺陷**（都不是素材的问题）：

1. 脚本把 V2 契约写死，于是完全合规的 V1 素材被判"尺寸不符"；
2. 版本校验的**反例**固定"改成 1"，而素材本来就是 V1，反例等于没改。

两条都已修：版本现在由**清单**决定（`atlasForVersion`），反例改成声明
**另一个**版本。V1 没有注视行，所以那一节对 V1 断言的是
"正确地什么也不给"（`lookFrameRect` 返回 null → 渲染器回落普通 idle）。

**这本身就是一条教训**：验证脚本里的"期望值"如果是从**某一批素材**
归纳出来的，它就会在那批素材之外误报。期望值要么来自契约
（`petAtlas.ts`），要么来自素材自身（`playableFrames`），
**不能是手填的常量**。

### 4.4 画面真的在动（不是"有画面但冻住"）

切帧错误的典型表现是**看起来有画面但不动**（时间基准被每帧重置、
帧索引恒为 0）。静态截图证明不了这一点，所以连拍 6 张比对：

```
帧 0：frameRect = {x:960, y:0}     ← idle 第 6 帧
帧 1：frameRect = {x:0,   y:0}     ← idle 第 1 帧
帧 2：frameRect = {x:192, y:624}   ← 第 3 行 = waving
帧 3：frameRect = {x:576, y:624}   ← waving
帧 4：frameRect = {x:0,   y:0}     ← 回 idle
帧 5：frameRect = {x:384, y:624}   ← waving

6 张截图里有 5 张互不相同 → 画面在变
```

**第 2 行那个 y=624 值得单独说**：它不是随机的，是 `waving` 那一行
（`624 / 208 = 3`）。也就是说那一轮里感知层推出了 `happy`，动作映射把
`happy` 映到 `waving`，舞台真的切到第 3 行并在其中推进帧。
**整条"感知 → 情绪 → 动作 → 帧"的链路是通的**，不是只有首帧能画。

产物：`docs/evidence/runtime/sprite/{pet.png,frame-0..5.png}`
（由 `scripts/capture-pet.mjs` 与 `capture-pet-frames.mjs` 生成）。

## 5 · 踩过的坑（都是"报错信息与真因无关"那一类）

### 5.1 CSP 拦住了自定义协议

`fetch('xiaoqi-pet://...')` 被 CSP 拒：

```
Connecting to 'xiaoqi-pet://sheet/spritesheet.webp' violates the following
Content Security Policy directive: "connect-src 'self' ws://localhost:* ..."
```

对策：在 `src/renderer/index.html` 的 `connect-src` 里加 `xiaoqi-pet:`。
**scheme 限定**，不是 `*`。

### 5.2 CORS 接着拦——而报错把人引向错误的方向

放开 CSP 之后撞上第二条：

```
Access to fetch at 'xiaoqi-pet://...' from origin 'file://' has been blocked by
CORS policy: Cross origin requests are only supported for protocol schemes:
chrome, chrome-extension, chrome-untrusted, data, http, https.
```

这句话会把人引向"要不要换成 http"——而真正缺的是
`registerSchemesAsPrivileged` 里的 **`corsEnabled: true`**，
以及响应头里必须显式给 `Access-Control-Allow-Origin: file://`
（`*` 对"不透明源"不生效，实测仍然失败）。

两条报错完全不同、指向也不同，但根因都在"自定义协议"这一件事上。

### 5.3 `@` 别名下的模块导入：`transformRequest` 不够用

验证脚本要把真源码 import 进 Node。`vite.transformRequest()` 只转译
**单个文件**，import 原样保留（且被重写成 `/src/...` 这种 Vite 内部路径）。
塞进 `data:` URL 之后 Node 会拿那个 data URL 当基准去解析，得到：

```
ERR_UNSUPPORTED_RESOLVE_REQUEST: Invalid relative URL or base scheme is not hierarchical
```

对策：用 Vite 的 `build()`（Rollup）先**打包**成自包含 ESM 再 import
（`scripts/lib/import-ts.mjs`）。

顺带一条：`import 'esbuild'` 在本仓库会 `ERR_MODULE_NOT_FOUND`——
esbuild 不是直接依赖（只有 Vite 内部那一份，pnpm 不提升）。

### 5.4 注视方向的 0° 是**正上**，不是正前方

图集规范如此。初版写成 `atan2(-offset.y, offset.x) + 90`，于是正上方算成
180°（正下方），**上下整体镜像**。是四个正方向的测试抓出来的。

正确式子：`atan2(offset.x, -offset.y)`。

### 5.5 骨架上的一处泄漏（由 lint 逼出来）

`await bootSpriteStage(...)` 期间（解码 14MB 的图，几十毫秒）组件可能
已经被卸载。那时 `stageRef.current` 还是 null，清理函数什么也不做——
而新建的舞台已经注册了 pointer 监听、建好了几十个帧纹理，
成了永远不会被释放的残留。

对策：契约里的 `destroy()` + 在 `await` 之前把"造好的舞台"记到一个
局部变量里，让清理函数能连它一起销毁。

## 6 · 尚未验证的部分（诚实清单）

- **多显示器与混合 DPI** 下的精灵图窗口定位：沿用程序化后端的路径，
  但没有在精灵图模式下单独实测。
- **`failed` / `jumping` 等动作的蒙版差异**：验证脚本确认了
  `jumping` 有独立蒙版，但没有逐个动作做实时穿透验证。
- 拖动在精灵图模式下**没有**单独的实时套件（程序化那套 2/2 通过，
  而指针手势代码是同一套语义、分别实现的两份）。
- **注视方向（V2 专属）没有端到端跑过**：真实素材是 V1，没有那两行。
  角度换算有单测、V1 的正确回落有断言，但"V2 素材上真的会转头"
  只有代码路径，没有实测。
- 蒙版点尺寸（约 14 像素）在**真实素材**上是否够细，只做了密度检查
  （75% 点亮、无异常），没有做逐点的人眼比对。若发现边缘手感偏糙，
  调 `MASK_COLS` / `MASK_ROWS` 即可（换算都是推出来的，不用改别处）。

## 7 · 怎么用

```bash
# 1. 生成一只合规的测试图集（程序化，非第三方素材）
pnpm pets:gen

# 2. 用测试图集起宠物
XIAOQI_PET_DIR=assets/pets/test-sprite pnpm dev

# 3. 用你自己下载/生成的图集
XIAOQI_PET_DIR=D:/pets/my-cat pnpm dev
```

素材目录里只放两个文件：

```
<宠物目录>/
  pet.json           元数据（spriteVersionNumber: 2 表示 V2）
  spritesheet.webp   图集（1536×2288，无损 RGBA；PNG 也接受）
```

`pet.json` 的 `license` 两种写法都认（裸字符串，或 Codex 官方的
`{ name, url, author }` 对象）。**授权信息会打进启动日志**：

```
[xiaoqi] 宠物形象：Synthetic Test Pet · xiaoqi（程序化生成） · CC0-1.0 · V2 图集
```

这不是装饰——素材授权决定能不能分发，必须在运行时可见。

### 素材从哪来

| 来源                                   | 授权情况                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------- |
| Codex 官方 `hatch-pet` skill 生成      | 取决于你用的底模与提示词                                                                    |
| `legeling/awesome-codex-pet`（239 只） | 代码 MIT，**素材大多 CC BY-NC 4.0（非商用）**；28 只 MIT、4 只 CC BY 4.0，**没有 MIT 的猫** |
| 自己画                                 | 你的                                                                                        |

⚠️ **本项目的立场**：仓库里**不附带**任何第三方宠物素材。
`assets/pets/` 下只有程序化生成的测试图集（CC0，且被 `.gitignore` 忽略）。
用户自带素材时，授权由用户自行负责——所以日志里要显示出来。
