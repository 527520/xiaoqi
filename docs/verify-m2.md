## 二试：调试面板（施工令明确要求的截图证据）

### 面板实际输出（`debug-panel.txt`）

```
[状态] +0s
   前台进程：msedge.exe  →  类别：浏览器
   空闲时长：152s
   系统状态：QUNS=5
   工作模式：weekend（周末）
   情绪：calm
   生理：精力 85% / 饥饿 20% / 无聊 15% / 社交 20%
   关系：好感 30% / 信任 40% / 默契 10%  →  强度 30% 基调 reserved
   同类工具连续：0s
   已运行：0s
[状态] +4s
   前台进程：msedge.exe  →  类别：浏览器
   ...
   情绪：happy                     ← 变了，所以又打了一整块
   关系：好感 30% / 信任 40% / 默契 10%  →  强度 30% 基调 reserved
```

### ★ 这里发现并修掉一个真实缺陷

面板最初在状态变化时**只打一行压缩摘要**，于是
「一个实时打印当前状态的调试面板」（施工令 §5 M2）实际上
**看不到大部分状态**——尤其新加的关系层一行都没有。

它之所以一直没被发现，是因为**日志确实有输出**：
`[状态] +4s msedge.exe → weekend｜情绪 happy｜…` 看起来完全正常，
只是少了后面八行明细。

**是 `verify-m2.mjs` 逐项核对"面板里该有哪些字段"时抓出来的**——
如果只断言"面板有输出"，这个缺陷会一直留着。

修法：状态**变化**时打完整面板（直接复用 `perception.describe()`，
不在日志这边另写一套格式化），只有在**心跳**时才压成一行
（心跳每 30 秒一次，展开成八行会把长时间运行的日志撑得没法翻）。

### 截图的局限（如实标注）

`mood-*.png` 是**渲染进程**的画面截图，只有 220×220。
宠物窗口是透明的、且面板文字并不画在屏幕上（它打到主进程日志），
所以截图里**看不到面板内容**。

因此：

- **`mood-{reserved,warm,attached}.png`** 证明的是"宠物确实画出来了"；
- **`debug-panel.txt`** 才是"面板在打印什么"的证据。

两样都在 `docs/evidence/runtime/m2/` 下。

## 三试：本轮补上的关系层（规格 M2 的最后一块）

规格 §5 M2 要求状态机覆盖「生理（精力/饥饿/无聊）、情绪（8 个）、
**关系（好感/信任/默契）**、工作模式（8 个）」。
前三项与第四项早已完成，**关系层此前完全不存在**（全仓库搜不到相关标识符）。
本轮补上 `core/relationship.ts`。

### 它是本项目最容易写歪的一个模块

关系是唯一一个"用户做了/没做什么会留下痕迹"的层，
离"宠物在评价用户"只有一步。ADR-0003 明令禁止那一步，
所以模块里立了三条硬约束，每条都有对应的断言：

| 约束                             | 断言                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| ① 关系**永不**改变"是否愿意回应" | `relationshipMood()` 的取值里没有"冷淡/拒绝"这一档（穷举） |
| ② "没互动"只是时间流逝，不是过错 | 取消呼吸提醒**不做任何减法**；工作模式不影响好感/信任方向  |
| ③ 回落必须远慢于增长             | 两周不掉两成；每天摸一两下就稳得住                         |

### ★ 初版的数值是错的，被自己的单测抓出来

初版取「好感每小时 -0.5 个百分点」，听起来很小，
但换算成天是 **-12%/天**，一周不管就掉掉三分之二——那正是"惩罚用户"。
断言「陪它几天攒的关系，放几个月才会淡掉」直接把它抓了出来。

重新标定后（以**月**为单位的心智模型）：

| 量   | 回落      | 含义                                       |
| ---- | --------- | ------------------------------------------ |
| 好感 | -1.2%/天  | 从满值掉到"想念"门槛（0.2）约 **3.5 个月** |
| 信任 | -0.5%/天  | 比好感更耐久                               |
| 默契 | -0.12%/天 | 一旦形成基本不消失（且随陪伴**自然上升**） |

一次互动给 1.5 个百分点（≈ 好感 30 小时的回落量）。
换算成体感：**每天随便摸它一两下就能维持住关系**，只有彻底放着几个月才会淡。

### 关系真的影响了画面（不是"传了个字段没人用"）

基调通过**调制已有动作的幅度**表达，不加新动作——
加新动作会让状态组合爆炸（8 情绪 × 3 基调 × 4 生理态），
而且用户分辨不出"这是默契版呼吸"。调节幅度则会被感觉成"它今天好像更黏人"。

| 基调       | 呼吸  | 摇摆 | 次级动作 | 前倾  | 眨眼间隔 |
| ---------- | ----- | ---- | -------- | ----- | -------- |
| `reserved` | 1×    | 1×   | 1×       | 0     | 4.4s     |
| `warm`     | 1.15× | 1.3× | 1.25×    | 0.012 | 3.4s     |
| `attached` | 1.35× | 1.6× | 1.5×     | 0.024 | 2.6s     |

`reserved` 全是 1 倍，即**什么都不改**——所以关系没建立时画面与从前完全一致。

数值刻意都很小（最大 1.6 倍）：关系是**长期**变量，表达必须含蓄，
一下子变化明显反而会让用户以为宠物坏了。

### 怎么验证它真的生效（防静默失效）

这一层最容易的失败方式不是算错，而是**接上了但没人用**：
`relationship.ts` 单测全绿、`perception.ts` 也接上了，
但主进程没推给渲染层，于是画面上什么都看不到，而所有测试仍然是绿的。

所以验证从**渲染进程那一侧**取状态核对，并单独锁三种基调各截一张图：

```
✅ ★ 主进程把关系基调推给了渲染层（不是只写了个没人调的模块）
✅ ★ 舞台里的基调与主进程推送的一致（传下来没被丢掉）
✅ 基调 reserved → 动画系数正确   {"breathScale":1,"swayScale":1,"fidgetScale":1,"lean":0}
✅ 基调 warm     → 动画系数正确   {"breathScale":1.15,"swayScale":1.3,"fidgetScale":1.25,"lean":0.012}
✅ 基调 attached → 动画系数正确   {"breathScale":1.35,"swayScale":1.6,"fidgetScale":1.5,"lean":0.024}
✅ ★ 三种基调的动画系数**互不相同**（关系确实改变了画面）
```

## 四试：点击链路的两个断言

```
✅ ★ 点击后交互动画被触发了（反应计时器从 0 变成正数）
     点击前 0 → 点击后 0.666
✅ ★ 交互动画自己结束了（回到待机，不会一直满帧空转）
     1.4 秒后 reactionRemaining = 0
```

第二条不是凑数：交互动画期间帧率会被抬到 60fps
（`FRAME_RATE.active`），如果计时器不归零，帧率预算会永远停在那一档，
宠物就会一直满帧空转——而施工令 §4.3⑩ 明确「耗电是隐形差评源」。

### 这一条最初是"测错了东西"

第一版用 `window.xiaoqi.notifyInteraction()` 触发，断言失败。
但**实现并没有问题**：那条桥只是"告诉主进程用户点了"
（用于记记忆、推进生理），它不经过 Pixi 的 `pointerup`，
因此本来就不会触发舞台上的弹跳。

修法是加一个会真的调用 `#trigger()` 的诊断钩子
（`window.__petInteract`），而不是去改实现迁就测试。
**"测错了东西"与"东西坏了"必须分清**，否则会把正确的代码改坏。

## 五试：事件驱动（休眠补偿）—— 一个正确性问题，不是打磨项

施工令 §5 M2 写的是「低频轮询 + **事件驱动**」。此前只有轮询，
没有任何事件源。补上 `powerMonitor` 之后发现这里藏着一个**真实缺陷**：

### 缺陷：合盖 8 小时会被算成"用户连续工作 8 小时"

轮询解决的是"多久看一眼"，它解决不了"这一眼与上一眼之间机器睡着了"。
合盖 8 小时再打开，`tick()` 算出 `elapsedMs = 8 小时`，
生理就按"用户连续工作 8 小时"推进：精力 -64 个百分点、饥饿 +40 个百分点。
宠物一睁眼就是一副快饿死的委屈样。

**这不只是观感问题**：它凭空造出了一段**不存在的用户行为**，
而 §1.2⑦ 明令「永不统计用户摸鱼时长、永不生成效率报告。
**宠物不衡量用户**」。所以它是一个必须修的正确性缺陷。

### 修法：两道防线

| 防线   | 位置                                         | 作用                       |
| ------ | -------------------------------------------- | -------------------------- |
| ① 事件 | `powerMonitor` 的 `resume` / `unlock-screen` | 显式告诉感知器"刚才睡着了" |
| ② 兜底 | `tick()` 里判断间隔 > 5 分钟                 | 事件在某些休眠形态下会漏   |

两道都要，是因为**代价不对称**：漏掉的后果是"宠物凭空受了一天罪"，
而多一道判断的成本只是一次比较。

阈值取 5 分钟：正常轮询是 2 秒，所以任何超过 5 分钟的间隔都只可能是
挂起/休眠/时钟跳变。留这么宽的余量是为了容忍系统卡顿与定时器节流。

### ★ 想念有上限：离开 12 天与离开 12 小时结算**完全相同**

休眠期间用户什么都没做，所以关系的结算必须是**温和且有封顶**的
（`SUSPEND_MISS_CAP_MS = 12 小时`）。断言直接锁住这一点：

```
✅ ★ 时间跳变超过阈值 → 判定为休眠，生理**不**按"连续工作"推进
✅ ★ 休眠期间的"想念"有上限——离开 12 天与离开 12 小时结算相同
✅ ★ 休眠不会把关系打到原点（出差两周回来关系还在）
✅ ★ lastSampleAt 不被补偿清零（外部要靠它算真实间隔）
```

这是 ADR-0003 在数值上的守卫：**想念不能变成记账**。
出差两周回来，关系该是"想你了"，而不是"你欠我两周"。

### 顺带修掉两条"推进方式不真实"的旧测试

「生理量随时间演进」与「休息时精力回升」原本是 `advance(1 小时)`
一次跳完，加了休眠补偿后立刻变红。但**实现没有问题**——
一次跳 1 小时正好落进"机器睡着了"那条分支，而那正是它该做的事。
改为按**真实轮询节奏**（每拍 2 秒）推进一小时。
这个改动同时让测试更接近真实运行，不是迁就实现的绕路。
