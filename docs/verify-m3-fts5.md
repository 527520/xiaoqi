# M3 前置：FTS5 中文检索能力复核（对 verification.md V1 的更正）

**复核日期**：2026-09-11
**触发原因**：本项目的数据库冒烟测试（施工令 §4.2 要求的那个）用 `MATCH '加班'`
查 `用户昨天也在加班` 返回 **0 条**，与 `docs/verification.md` V1 的结论矛盾。
两者只能有一个对。

**复现命令**（全部已提交进仓库，任何人可跑一遍反驳我）：


## 一、V1 那条"中文子串检索可用"**不成立**（本条为更正）

V1 原文：

> **FTS5 全文检索可用**：`MATCH '加班'` 命中"用户昨天也在加班"
> 中文分词：FTS5 默认 `unicode61` 对中文按字切分，子串检索可用

原样复刻同一个用例：

```
MATCH '加班'                    → 0 条     ← V1 声称这里命中 1 条
MATCH '加' / '昨天' / '也在加班'  → 均 0 条
MATCH '用户昨天也在加班'          → 1 条     ← 用**整句**查才命中
```

**根因**（用 `fts5vocab` 直接读 token，不靠推断）：

```
"用户昨天也在加班"      → 1 个 token: ["用户昨天也在加班"]
"加班"                → 1 个 token: ["加班"]
"用户 昨天 加班"        → 3 个 token: ["加班","昨天","用户"]
"用户，昨天：加班"       → 3 个 token: ["加班","昨天","用户"]
```

结论很清楚：`unicode61` **按"词"切分，不是按"字"切分**。
**中文没有词间空格**，所以一整句连续中文 = **一个 token**；
而中文标点与空格**是**分隔符，有分隔时切分就正常
（`"用户，昨天：加班"` 切出 3 个 token 就是证据）。

因此"能查到"只发生在**拿原句查原句**。V1 当时很可能验的正是这个——
**把"能存取"误当成了"能检索"**。

> 我刻意保留余地：我无法知道当时那次运行的输入到底是什么，
> 只能说明**该结论按它写下来的用法无法复现**。

## 二、换分词器也解决不了（逐项实测）

**trigram**：切成三字滑窗，但 `MATCH` 会把**查询串也按同一分词器切**，
再要求 token 集合匹配：

```
正文 tokens: ["也在加","在加班","天也在","户昨天","昨天也","用户昨"]
MATCH "加班"    → 0 条   ← "加班"切成 1 个 token，正文里没有这个 token
MATCH "也在加班" → 1 条   ← 切出 2 个 trigram，都在正文里
MATCH "昨天"    → 0 条
```

即 **trigram 只支持长度 ≥3 的子串**。而中文里最关键的检索词恰恰大多是
2 字（加班、开会、摸鱼、抹茶）——**正好落在它支持不了的那一档**。

**前缀查询**也救不了：前缀只能匹配 **token 的开头**。

```
[unicode61] MATCH '加班*' → 0     ← 整句是 1 个 token，"加班"在中间
[unicode61] MATCH '用户*' → 1     ← 只有从整句开头算才叫前缀
```

出现在句子中间的词，**永远不可能**被前缀查询命中。

**ICU 分词器不可用**（这份 SQLite 未编译 ICU）：

```
SQLite 版本：3.53.4
编译选项相关：ENABLE_FTS3 / ENABLE_FTS3_PARENTHESIS / ENABLE_FTS4 / ENABLE_FTS5 / THREADSAFE=2
分词器 unicode61 / ascii / porter / trigram → 可用
分词器 icu → 不可用（no such tokenizer: icu）
```

**外部原生分词器也不可行**：社区针对这个问题的标准解法就是自写分词器
（[fts5-simple](https://github.com/zmy12006/sqlite-fts-simple)、
[better-trigram](https://github.com/streetwriters/sqlite-better-trigram)），
那是**原生扩展**——而本机没有任何 C++ 编译器（施工令 §3），装不了也编不了。
另有[一个 PR](https://github.com/openclaw/openclaw/pull/11689) 正是给 CJK 做**按字**分词，
从侧面确认"默认分词器对 CJK 不可用"是已知问题。

## 三、LIKE 的真实表现（含性能，用来替代猜测）

```
=== 命中率（测试数据里实际存在的词 5 个）===
A. 默认 FTS5（unicode61）      0/5
B. trigram FTS5                0/5
C. trigram + 短查询 LIKE 兜底   5/5   ← 靠的其实是 LIKE
D. 纯 LIKE（对照）             5/5
```

> 脚本输出里写的是 `/7`：查询词表含 `开会`、`摸鱼`，而这两个词
> **本来就不在测试数据里**（数据写的是"讨厌开长会"）。
> 按数据里真实存在的词算，**LIKE 满分，两种 FTS5 都是 0**。

```
=== LIKE 的真实大小写行为 ===
默认 '%abc%'            → 命中（大小写不敏感）
case_sensitive_like=ON  → 不命中
中文 '%加班%'            → 命中
```

```
=== 性能 ===
5000 条：  LIKE '%加班%' 全表扫描 200 次 → 总 48.1ms，单次 0.240ms

20000 条逐项对照：
无索引          子串 '%加班%'  0.917ms/次
有索引          子串 '%加班%'  0.924ms/次   ← 索引没用上（SCAN）
有索引 + CS     子串 '%加班%'  0.909ms/次   ← 前导 % 让索引必然失效
有索引 + CS     前缀 '第1条%'  0.008ms/次   ← 只有前缀能走索引
```

`EXPLAIN QUERY PLAN` 直接确认：

```
[默认] 子串 : SCAN notes
[CS]   子串 : SCAN notes
[CS]   前缀 : SEARCH notes USING COVERING INDEX idx_notes_content
```

**所以"给内容列建索引让 LIKE 变快"行不通**：记忆检索要的是**子串**
（"加班"出现在句子中间），而前导通配符 `%` 让任何 B-tree 索引必然失效。
唯一能走索引的是前缀查询，而中文句子里词几乎不在句首。

## 四、那么代价到底是多少

子串检索**就是全表扫描**，所以唯一的问题是"表有多大"。实测与外推：

| 记忆条数 | 单次子串检索     |
| -------- | ---------------- |
| 1,000    | ≈ 0.05ms（外推） |
| 5,000    | 0.240ms（实测）  |
| 20,000   | 0.917ms（实测）  |

规格说记忆规模是**千条级**。在 1000 条上每次约 0.05ms——
即使每敲一个键都查一次，也远低于一帧的时间。

## 五、对 M3 的影响与我的结论

**"用 FTS5 做中文子串检索"在本机不可行**，且不是版本问题——
是 FTS5 分词模型与中文书写方式的结构性错配，换机器也一样
（除非编一个原生分词器，而这台机器没有编译器）。

但规格给的**理由**我完全同意，而且它成立：

- **不引入向量库**（千条级用不上，且向量检索不可解释）；
- 需要的是**可解释的子串检索 + 时间/情绪/标签过滤**。

不成立的是"必须用 FTS5"这个**手段**。

**我的结论：用 LIKE 做子串检索，并打开 `case_sensitive_like`**
（中文无大小写，零语义损失，且顺带让前缀查询能走索引）。
不建 FTS 表——它既命不中（0/5），又要额外维护触发器保持同步。

方案取舍与留给用户拍板的选项见 `docs/BLOCKERS.md` 的 **B-2**。
