# M3 前置：FTS5 中文检索能力复核（对 verification.md V1 的更正）

**复核日期**：2026-09-11
**触发原因**：本项目的数据库冒烟测试用 `MATCH '加班'` 查 `用户昨天也在加班` 返回 0 条，
与 `docs/verification.md` V1 的结论矛盾。两者只能有一个对。

**复现命令**：

```
node scripts/recheck-v1-fts5.mjs      # 原样复刻 V1 的用例
node scripts/probe-fts5-chinese.mjs   # 看分词器到底切出了什么
node scripts/probe-fts5-strategy.mjs  # 比较三条实现路线的实际命中率
```

---

## 结论：V1 那条"中文子串检索可用"**不成立**，本条为更正

V1 原文：

> **FTS5 全文检索可用**：`MATCH '加班'` 命中"用户昨天也在加班"
> 中文分词：FTS5 默认 `unicode61` 对中文按字切分，子串检索可用

实测（原样复刻同一个用例）：

```
MATCH '加班'                      → 0 条     ← V1 声称这里命中 1 条
MATCH '加'                        → 0 条
MATCH '昨天'                      → 0 条
MATCH '也在加班'                   → 0 条
MATCH '用户昨天也在加班'            → 1 条     ← 用**整句**查才命中
```

**根因**：FTS5 的默认分词器（`unicode61`）**并不对中文按字切分**。
它把连续的中文当成**一个 token**。用 `fts5vocab` 直接读切出来的 token 可以确认：

```
=== 默认（unicode61）===
  切出的 token（1 个）： 用户昨天也在加班
```

所以"能查到"只发生在**拿原句查原句**。
`docs/verification.md` V1 当时验的很可能正是这个——"原句能查到原句"，
于是被记成了"中文子串检索可用"。**这是把"能存取"误当成了"能检索"。**

> 这段话刻意保留判断的余地：我无法知道当时那次运行的输入到底是什么，
> 只能说明**该结论按它写下来的用法无法复现**。

---

## 换分词器也解决不了

```
=== trigram 分词器 ===
  切出的 token（6 个）： 也在加 | 在加班 | 天也在 | 户昨天 | 昨天也 | 用户昨
```

trigram 切成三字滑窗，看起来有希望，但实际查询：

| 查询               | 结果                                                       |
| ------------------ | ---------------------------------------------------------- |
| `加班`（2 字）     | **0 条** —— "加班"本身就是一个 trigram token，内部没有滑窗 |
| `也在加班`（4 字） | 1 条                                                       |

即 **trigram 只支持长度 ≥3 的子串**。而中文里最关键的检索词恰恰大多是
2 字（加班、开会、摸鱼、抹茶）——**正好落在它支持不了的那一档**。

三条路线的命中率对照（测试数据里实际存在的词 5 个）：

| 方案                          | 命中                       |
| ----------------------------- | -------------------------- |
| A. 默认 FTS5（unicode61）     | **0/5**                    |
| B. trigram FTS5               | **0/5**                    |
| C. trigram + 短查询 LIKE 兜底 | 5/5（**靠的其实是 LIKE**） |
| D. 纯 LIKE（对照）            | **5/5**                    |

> 注：脚本输出里写的是 `/7`，因为查询词表里有 2 个词（`开会`、`摸鱼`）
> **本来就不在测试数据里**（数据里写的是"讨厌开长会"）。按数据里真实存在的词算，
> LIKE 是满分，两种 FTS5 都是 0。

---

## 对 M3 的影响

**"用 FTS5 做中文子串检索"在本机不可行。** 这不是偏好问题，
而是该手段达不到它被选中的目的。

规格给的理由仍然成立且我完全同意：

- **不引入向量库**（千条级规模用不上，且向量检索不可解释）；
- 需要的是**可解释的子串检索 + 时间/情绪/标签过滤**。

不成立的是"必须用 FTS5"这个手段。`LIKE '%词%'` 在千条级规模下：

- 命中率满分（1 字起就能查）；
- 全表扫描成本在微秒量级；
- 对中文与大小写的行为直接、可解释。

方案取舍与需要用户拍板的三个选项见 `docs/BLOCKERS.md` 的 **B-2**。
