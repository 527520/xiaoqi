## M0 / M1（工程骨架与垂直切片）

### 2026-09-11 · 依赖版本按 peer 依赖交集钉死，不取 npm `latest`

|            |                                                                                                                                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **决策**   | TypeScript **6.0.3**、Vite **7.3.6**、`@vitejs/plugin-react` **5.2.0**、ESLint **10.10.0**、`typescript-eslint` **8.70**、Electron **44.3.0**、pixi.js **8.20.1**、React **19.3.0**                                                                                |
| **备选**   | 全部取 `latest`：TypeScript 7.0.2、Vite 8.3.0、`@vitejs/plugin-react` 6.1.1                                                                                                                                                                                        |
| **为什么** | 取 `latest` 直接装不上或装出坏组合：`typescript-eslint` 的 peer 是 `typescript <6.1.0`（**TypeScript 7 不可用**）；`electron-vite@5` 要 `vite ≤7`，而 `@vitejs/plugin-react@6` 要 `vite 8`，二者互斥。交集唯一解就是上表。**先查 peer 再装**，比装完再拆便宜得多。 |

### 2026-09-11 · preload 强制产出 CommonJS（`.cjs`），不用默认的 `.mjs`

|            |                                                                                                                                                                                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `electron.vite.config.ts` 里给 preload 显式设 `format: 'cjs'` + `entryFileNames: '[name].cjs'`；主进程按 `../preload/index.cjs` 加载                                                                                                                                                                 |
| **备选**   | 保持 electron-vite 默认（根 `package.json` 是 `"type": "module"`，于是产成 `index.mjs`）                                                                                                                                                                                                             |
| **为什么** | 渲染进程是 `sandbox: true`，而**沙箱化的 preload 不支持 ESM**。后果不是报错，而是 preload **静默不执行**：`window.xiaoqi` 不存在，渲染进程第一句用它就抛错，报错位置看起来与 preload 毫无关系，表象只是"宠物没渲染出来"。本项目实际踩中了这个坑（构建产物是 `index.mjs`，而主进程在找 `index.js`）。 |

### 2026-09-11 · 点击穿透用光标轮询，**不启用** `setIgnoreMouseEvents` 的 forward

|            |                                                                                                                                                                                                                                                                                                 |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 主进程每 80ms 轮询 `screen.getCursorScreenPoint()`，与宠物轮廓比对后翻转 `setIgnoreMouseEvents(bool)`，**从不带 `{ forward: true }`**                                                                                                                                                           |
| **备选**   | `setIgnoreMouseEvents(true, { forward: true })` + 渲染进程用转发事件感知光标（这是 `OpenPetsHQ/openpets` 与 `ayangweb/BongoCat` 的实际做法）                                                                                                                                                    |
| **为什么** | 施工令 §4.3③ 已列明转发在 Windows 上有三个**未修复**失效面（#48035 光标闪烁、#49982 崩溃后穿透状态卡死、#53026 提权窗口下转发暂停）。轮询方案不开转发，因此对这三个失效面**结构性免疫**——不是"更稳"，是根本没有那个失效路径。代价是 80ms 的轮询开销（可忽略）与最长 80ms 的判定延迟（足够快）。 |

### 2026-09-11 · 判定逻辑全部下沉到 `core/` 纯函数，执行留在 `window/`

|            |                                                                                                                                                                                                                                                                               |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | "该不该穿透""该不该静默""该不该降帧"三个判定做成纯函数放 `src/main/core/` 并单测；`src/main/window/petWindow.ts` 只负责把结论执行下去                                                                                                                                         |
| **备选**   | 判定与 Electron 调用写在一起（更短、更"直接"）                                                                                                                                                                                                                                |
| **为什么** | M1 的技术风险集中在"判定对不对"，而判定是**唯一可以自动化验证**的那一半。分开之后，`cursorRouter` / `modeGate` / `frameRate` 各有完整单测（69 项），只剩"有没有真的调用 API"需要实机验证——而那部分用 `scripts/verify-clickthrough.mjs` 端到端覆盖。混在一起则两者都无法验证。 |

### 2026-09-11 · 全局快捷键用 `Ctrl+Shift+H` / `Ctrl+Shift+J`

|            |                                                                                                                                                                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 隐身 `CommandOrControl+Shift+H`，显示 `CommandOrControl+Shift+J`；注册失败时**明确打日志**                                                                                                                                                                 |
| **备选**   | 单一键 `Ctrl+Shift+H` 做切换（toggle）；或不注册第二个                                                                                                                                                                                                     |
| **为什么** | 施工令 §9.4 要求"一键隐身必须可靠且随手可及"。用**两个独立**键而不是一个切换键，是因为在"被围观"的紧张场景下，用户需要的是**确定的结果**（按下去一定消失），而不是"取决于当前状态"的结果。注册失败必须说出来——静默失败会让用户以为"按了没反应是宠物坏了"。 |

### 2026-09-11 · 图标程序化生成，并与宠物几何做**防漂移自检**

|            |                                                                                                                                                                                                                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `scripts/generate-icons.mjs` 用代码绘制托盘/应用图标并手写 PNG 编码（zlib）；启动时读 `src/shared/constants.ts` 核对几何是否一致，不一致即报错退出                                                                                                                                           |
| **备选**   | 手绘一张 PNG 提交进仓库；或引入 `sharp` / `canvas`                                                                                                                                                                                                                                           |
| **为什么** | 三个理由：①本机**没有 C++ 编译器**，原生图形库装不上；②手绘位图会与宠物几何**静默漂移**（改了宠物形状但忘了改图标）；③让仓库里不出现"来源不明的二进制素材"，许可证干净。自检把"忘了同步"从视觉不一致变成**响亮的构建失败**——而且这个自检**经过反向验证**（故意改错一处，确认它退出码为 1）。 |

### 2026-09-11 · 诊断能力写进产品（CDP + 分层可见性 + 错误上报）

|            |                                                                                                                                                                                                                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | ①渲染进程把未捕获错误连同**堆栈**经 `sendSync` 送到主进程日志；②`window.__petDebug()` 暴露只读的舞台内部状态；③`window.__petLayer()` 可单独开关图层以便分层截图；④`scripts/attach-cdp.mjs` 用 CDP 连真实应用（**不打开 DevTools 窗口**）                                                                                                                      |
| **备选**   | 靠 `console.log` + 反复改代码猜；或直接开 DevTools                                                                                                                                                                                                                                                                                                            |
| **为什么** | 施工令 §4.3② 实测**DevTools 一打开透明窗就不透明**，等于把渲染进程的常规调试手段废掉了；而 Chromium 的 `console-message` 事件**不带堆栈**（对未捕获的 Promise 拒绝，`sourceId`/`lineNumber` 都是空的）。不补上这套能力，"宠物没显示"就是纯黑盒。**实际回报极高**：M1 排查中正是靠它定位了库名写错、Pixi CSP、以及眼睛不渲染三个 bug；仅靠猜的那几轮全部猜错。 |

### 2026-09-11 · 不用 `pixi.js` 的 `Application` 之外的抽象层；眼睛不用中间 `Container`

|            |                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 眼睛直接是挂在 `#root` 上的 `Graphics`（形状画在局部原点、靠 `position` 平移），**不套中间 `Container`、不使用 `pivot`**                                                                                                                                                                                                                                                                                |
| **备选**   | 每只眼睛一个 `Container`，用 `pivot` 定缩放锚点、`position` 定落点（更"面向对象"）                                                                                                                                                                                                                                                                                                                      |
| **为什么** | 实测：套上中间 `Container` 后，眼睛**一个像素都不画**，而且不报任何错——`visible`/`renderable` 全为 true、`getLocalBounds()` 与 `worldTransform` 都"看起来正确"（tx=90, ty=133）。同一段绘制代码换成直接挂 root 立刻正常。**具体根因我没有定位到**（只确认了规避方式），因此选择绕开这条路径的写法。另外单独确认了 Pixi v8 的 `position` 会被 `pivot` 偏移：`pivot == position` 会把内容画到父容器原点。 |

### 2026-09-11 · 静默态复用"可见的小点"，而不是隐藏窗口

|            |                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 全屏/锁屏时形态切到 `silent`：窗口**保持可见**、缩成 0.3 倍并慢速呼吸、帧率降到 4fps、停止交互动画                                                                                                                                                                                                                                                                                                                |
| **备选**   | 全屏时直接隐藏窗口（`hidden`），退出全屏再显示                                                                                                                                                                                                                                                                                                                                                                    |
| **为什么** | 规格已定：施工令 §9.2「QUNS `{1,2,3,4}` 即静默」，而 `CONTEXT.md` 把**静默**定义为"降低存在感但**仍然可见**"，并给了理由——「用户能看见它，因此知道它没崩」（§9.5「它可以安静，但不能装死」）。隐藏窗口会让宠物在用户全屏工作一段时间后"消失得无影无踪"，回到桌面时不确定它是否还活着。**这与主要参考项目相反**（openpets 选择全屏时保持在内容之上），但我们的规格已经选定了静默，因此这不构成需要外部拍板的分歧。 |

### 2026-09-11 · 待机帧率定为 8fps

|            |                                                                                                                                                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `FRAME_RATE.idle = 8`（交互动画 60、静默 4）                                                                                                                                                                         |
| **备选**   | 12fps（初版实现值）                                                                                                                                                                                                  |
| **为什么** | 施工令 §4.3⑩ 的硬要求是待机 **≤10fps**。初版写 12fps 是**违反规格**的，而且是被自己的单测断言（`expect(fps).toBeLessThanOrEqual(10)`）抓出来的——不是靠人眼审阅。呼吸周期 2.6s，8fps 下每周期约 21 帧，已经足够平滑。 |
