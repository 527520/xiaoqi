### 2026-09-11 · 依赖版本按 peer 依赖交集钉死，不取 npm `latest`

| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **决策**   | TypeScript **6.0.3**、Vite **7.3.6**、`@vitejs/plugin-react` **5.2.0**、ESLint **10.10.0**、`typescript-eslint` **8.70**、Electron **44.3.0**、pixi.js **8.20.1**、React **19.3.0**                                                                                |

### 2026-09-11 · preload 强制产出 CommonJS（`.cjs`），不用默认的 `.mjs`

|            |                                                                                                                                                                                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `electron.vite.config.ts` 里给 preload 显式设 `format: 'cjs'` + `entryFileNames: '[name].cjs'`；主进程按 `../preload/index.cjs` 加载                                                                                                                                                                 |
| **备选**   | 保持 electron-vite 默认（根 `package.json` 是 `"type": "module"`，于是产成 `index.mjs`）                                                                                                                                                                                                             |
| **为什么** | 渲染进程是 `sandbox: true`，而**沙箱化的 preload 不支持 ESM**。后果不是报错，而是 preload **静默不执行**：`window.xiaoqi` 不存在，渲染进程第一句用它就抛错，报错位置看起来与 preload 毫无关系，表象只是"宠物没渲染出来"。本项目实际踩中了这个坑（构建产物是 `index.mjs`，而主进程在找 `index.js`）。 |

### 2026-09-11 · 点击穿透用光标轮询，**不启用** `setIgnoreMouseEvents` 的 forward

|            |                                                                                                                                                                                                                                                                                                 |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 主进程每 80ms 轮询 `screen.getCursorScreenPoint()`，与宠物轮廓比对后翻转 `setIgnoreMouseEvents(bool)`，**从不带 `{ forward: true }`**                                                                                                                                                           |
| **备选**   | `setIgnoreMouseEvents(true, { forward: true })` + 渲染进程用转发事件感知光标（这是 `OpenPetsHQ/openpets` 与 `ayangweb/BongoCat` 的实际做法）                                                                                                                                                    |
| **为什么** | 施工令 §4.3③ 已列明转发在 Windows 上有三个**未修复**失效面（#48035 光标闪烁、#49982 崩溃后穿透状态卡死、#53026 提权窗口下转发暂停）。轮询方案不开转发，因此对这三个失效面**结构性免疫**——不是"更稳"，是根本没有那个失效路径。代价是 80ms 的轮询开销（可忽略）与最长 80ms 的判定延迟（足够快）。 |

### 2026-09-12 · 记忆检索用 `LIKE` 子串匹配，**不建 FTS5 表**（可逆）

|            |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | 施工令 §5 M3 要求的"中文子串检索"用 `content LIKE '%词%' ESCAPE '\'` 实现；打开 `case_sensitive_like` 以便前缀查询可走索引；**不建 FTS5 虚表**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **备选**   | A 纯 LIKE（选中）／B 保留 FTS5 表只当长片段索引、检索主路径仍走 LIKE／C 自写 bigram 分词，写入时把中文切成 2 字滑窗存进 FTS5 表                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **为什么** | 施工令 §5 写的是「FTS5 全文检索」，但**它真正要的能力是"中文子串检索"，而 FTS5 在本机做不到这件事**。实测（`docs/verify-m3-fts5.md`，6 个可复现脚本，5 种策略横向对比）：默认 `unicode61` 把连续汉字当成**一个 token**（`MATCH '加班'` → 0/5，整句才命中），`trigram` 同样漏 2 字词（`MATCH '加班'` → 0），前缀查询救不了句中词（`MATCH '加班*'` → 0），ICU 分词器本机没有，自写原生分词器**没有 C++ 编译器**。唯一 5/5 命中的是 LIKE。**且这不是版本问题，是 FTS5 分词模型与中文书写方式的结构性错配**，换机器也一样。性能上 LIKE 走全表扫描，但实测 5,000 条 0.240ms／20,000 条 0.917ms，而规格说记忆规模是**千条级**（≈0.05ms），完全无感——用规格自己给的规模假设，B/C 两个方案换来的"用上了 FTS5"没有任何可观测收益，只多出同步触发器或自维护分词器的出错面。 |
| **可逆性** | **可逆，且改动面被刻意收窄**：检索只发生在 `src/main/core/memory/store.ts` 内部一个方法里，`MemoryStore` 对外接口（`addEpisodic` / `search` / `deleteMemory` …）与 SQL 表结构都不含 FTS 概念。若日后要改成 C（bigram），**只需改 `store.ts` 的建表与 `search` 内部，调用方一行不动**。                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

> **为什么这一条我自行拍板了**：§8 第 3 类"发现规格自相矛盾"要求上报，我已按 B-2 上报且**第二轮查证也已完成**。但上报的是"规格给的**手段**做不到规格要的**能力**"这一矛盾，不是"要什么能力"有分歧——能力（中文子串检索）是规格明写的、无歧义。因此这里选的是**实现手段**，属于 §8 授权的自主决定范围；同时它可逆、且改动面已收窄到单个文件，选错的代价被压到最低。

### 2026-09-12 · 删除记忆用 `secure_delete` + `VACUUM`，**不设软删除标记**

|            |                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `openMemoryDatabase()` 打开即设 `PRAGMA secure_delete = ON`；表结构里**没有任何** `deleted_at` / `is_deleted` 列，删除就是 `DELETE` + `VACUUM`，且删除路径**不把内容写进日志**（只记"删除了一条记忆"这一事实）                                                                                                                                                                                                   |
| **备选**   | 软删除（标记 + 查询时过滤），或硬删除但不设 `secure_delete`                                                                                                                                                                                                                                                                                                                                                      |
| **为什么** | 施工令 §1.2⑪ 是**硬约束**：「删掉的记忆必须真的消失，不得在日志或缓存中留痕」。软删除与之**直接冲突**——数据仍在文件里，只是被查询过滤掉了，任何能看到数据库文件的人都能读出来。不设 `secure_delete` 时 SQLite 只把页标记为可复用，原文会**留在文件里直到该页被覆写**。因此两项都必要。**这条约束是"删除必须可验证"的**，所以配了 `scripts/verify-memory-delete.mjs`：把真库文件当**二进制**扫原文的 UTF-8 字节。 |
| **验证**   | `pnpm verify:memory-delete` —— 8 项断言全过。★ 关键设计：脚本里有**对照组**，要求"没被删的那条必须仍能扫到"（实测偏移 8154）。没有这条，"扫不到"可能只是因为扫描方法无效（假阳性），整个验证就不算数。                                                                                                                                                                                                           |

### 2026-09-12 · 记忆检索**不给 `content` 建索引**

|            |                                                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **决策**   | `memories` 表只在 `occurred_at` 上建索引，`content` 上**不建任何索引**                                                                                                                                                                      |
| **备选**   | 给 `content` 建普通索引；或建 `content` 前缀索引                                                                                                                                                                                            |
| **为什么** | 检索模式是 `LIKE '%词%'`——**前导 `%` 使 B-tree 索引在结构上不可用**，`EXPLAIN QUERY PLAN` 实测任何子串查询都是 `SCAN`。建了也不会被用到，只会拖慢写入并占空间。这是"看起来该建"但**实测不该建**的典型：判断依据是查询计划的输出，不是直觉。 |
