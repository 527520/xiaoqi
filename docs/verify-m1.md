## 证据 7 · 待机降帧

`frameRate.test.ts`（12 项）断言：

```
✓ 待机时不是 60fps                        → FRAME_RATE.idle = 8（≤10，符合 §4.3⑩）
✓ 有交互动画时才升到 60fps
✓ 静默态比待机还低（silent = 4）
✓ 窗口不可见时帧率为 0（语义是"停更"）
✓ 隐身形态时帧率为 0，即使窗口还来不及隐藏
✓ 不可见优先于"正在动画"
✓ 两个字段不同但帧率相同的组合，不算变化（避免重复写 ticker.maxFPS）
```

**实测到的 bug**：初版 `FRAME_RATE.idle = 12`，**违反了 §4.3⑩ 的硬要求（≤10fps）**。
这是被单测断言 `expect(fps).toBeLessThanOrEqual(10)` 抓出来的，不是靠人眼审阅。

**一个反直觉的实现陷阱**（已写进代码注释）：Pixi 的 `ticker.maxFPS = 0`
意思是**不限帧**，不是暂停。因此 `frameRate` 返回的 `0`（语义为"停更"）
在渲染进程里被**夹到 1**，绝不能直接写进 `maxFPS`——
否则隐藏/隐身状态会变成满帧空转，正好与省电目标相反。

## M1 排查中修掉的真实 bug（每个都"不报错"）

按施工令 §7 的精神，这些记录比结论更有价值——它们都是**静默失效**：

| #   | 现象                                                           | 根因                                                                                         | 为什么难发现                                                                        |
| --- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 1   | 应用启动即崩                                                   | `SHQueryUserNotificationState` 挂在了 `user32.dll`（应在 `shell32.dll`）                     | 报错只说"找不到函数"，**不提库名写错**                                              |
| 2   | 宠物完全不渲染                                                 | Pixi 需要 `unsafe-eval`，而严格 CSP 禁掉了它                                                 | 错误发生在 `Application.init()` 的 Promise 里；窗口本身正常，表象只是"什么都没显示" |
| 3   | preload 不执行                                                 | `"type":"module"` 让 preload 产成 `.mjs`，而**沙箱 preload 不支持 ESM**                      | preload 静默不执行，报错出现在渲染进程一个看起来无关的地方                          |
| 4   | **宠物没有眼睛**                                               | 见下方"关于 #4 的诚实说明"——**根因未定位**                                                   | 读到的场景图"看起来完全正常"，控制台干净                                            |
| 5   | Pixi `pivot == position` 画到原点                              | v8 的 `position` **被 `pivot` 偏移**                                                         | 与"pivot 是旋转锚点、position 是落点"的直觉相反                                     |
| 6   | 待机 12fps 违反规格                                            | 初版常量写错                                                                                 | 只看代码看不出来，靠单测断言卡住                                                    |
| 7   | `pnpm dev` 下渲染进程报 `this._cancelResize is not a function` | React 19 StrictMode 挂载两次，对**尚未 `init()` 完成**的 Pixi `Application` 调了 `destroy()` | 生产构建不复现（没有双挂载），只在开发模式出现                                      |

### 关于 #4 的诚实说明（这一条我改了结论）

最初我把"眼睛不渲染"归因为**"给眼睛套一层中间 `Container` 就不画"**。
后来发现了 **#7** 这个真实 bug，它同时污染了当时的排查手段：

`window.__petDebug` 钩子在 StrictMode 的"挂载 → 卸载 → 再挂载"过程中，
可能仍然指向**已经被 `destroy()` 的第一个 `Application`**。而那个已销毁实例的
场景图恰好也"看起来完全正常"（`visible`/`renderable` 全 true、世界坐标也对）。
**当时读到的快照很可能来自一个死实例。**

因此：

- **不能再说"容器有 bug"** —— 那条观察有未排除的混淆因素，
  我没有在干净条件下复现过它。代码注释里已按此更正。
- 仍然保留当前写法（不套容器、不用 `pivot`），但理由收窄为一条独立成立的事实：
  Pixi v8 的 `position` 会被 `pivot` 偏移，`pivot == position` 会把内容画到父容器原点。
  当前写法让"容器原点 = 眼睛中心 = 缩放锚点"三者重合，绕开这一点，且更少间接。
- Pixi v8 的 `pivot` 语义已用受控最小复现**独立量过**（见 `docs/DECISIONS.md`），
  那部分结论不受本次更正影响。

**这条更正本身是本轮最有价值的产出之一**：一个会污染所有诊断读数的 bug，
比它引发的那个表面现象重要得多。

**关于排查手段**：本机**不能靠开 DevTools 排查渲染**（施工令 §4.3② 实测：
DevTools 打开时透明窗变不透明），而 Chromium 的 `console-message` 事件**不带堆栈**
（对未捕获的 Promise 拒绝，`sourceId`/`lineNumber` 都是空的）。
因此本轮补了三样诊断能力（见 `docs/DECISIONS.md`）：
渲染进程错误+堆栈经 `sendSync` 送主进程日志、`window.__petDebug()` 只读快照、
以及 `scripts/attach-cdp.mjs`（用 CDP 连真实应用，**不打开 DevTools 窗口**）。
#1–#4 全部是靠这套能力定位的；仅靠"改代码 + 猜"的那几轮全部猜错。

## 证据 9 · 外观与动效重做

### 9.1 设计方向的改向

初版配色是「暖奶油身体 + 深棕描边 + 珊瑚腮红」——那是这类产品最顺手的默认长相，
也最容易被一眼归进"模板感桌宠"。现在：

- 主体 **云蓝灰 + 自上而下的渐变**（上半受光、下半落影），从"一块平涂"变成"有厚度"；
- 描边用**墨蓝**（纯黑在透明窗上显脏，深棕又把它拉回毛绒玩具）；
- **暖色只留给眼睛与腮红**：眼睛是**琥珀 + 深棕瞳孔 + 双高光**。
  纯黑眼睛看起来是"洞"，琥珀才像玻璃珠。整只宠物只有这两处是暖的，
  视线于是自然落在脸上。
- 耳朵从**圆**改成本体与图标一致的**圆角尖三角**（圆耳 + 圆身读起来像老鼠）；
- 身体收窄成上窄下宽的蛋形，重心在下。

截图：`docs/evidence/pet-new-design.png`。

> 这条尾巴改了**五版**才成立，过程记在 `PetStage.ts` 的 `TAIL_SHAPE` 注释里：
> 圆团 → "侧面的瘤"；两点收尖 → "鲨鱼鳍"；末端大钩 → 自交出黑线；
> 沿中心线放样 → 仍与身体糊成一片读成"鳍"；
> 最终版 = 一个**明确分离**的圆角尖椭圆，只从身体后面探出一点。
> 结论：露出一点点、形状自洽、与身体有明显分界——三件事同时满足才读得出"尾巴"。

### 9.2 动效

| 动效        | 做法                                                       | 为什么这么做                                               |
| ----------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| 呼吸        | **体积守恒的 squash & stretch**，锚点在身体底部中心        | 不像"飘"，像"呼吸"；锚点在底部才有"踩在地上"的感觉         |
| 耳朵 / 尾巴 | **相位滞后**的次级动作（耳朵滞后 0.18s，尾巴更快更大幅度） | 同相位摆动读起来像整块图在转；滞后才有"身体动带动了耳朵"   |
| 眨眼        | 三角形曲线，只在眨眼中点闭合；间隔 2.4–7s 随机             | 固定节奏像机器；旧实现"只要在眨就压扁"导致眼睛几乎永远闭着 |
| 被点一下    | **眼睛画成笑弧** + 非对称弹跳包络（起手快、回落慢）        | 压扁只是"变小"，弧线才是"笑"；对称曲线没有重量感           |
| 待机降帧    | 8fps（静默 4fps，隐藏停更）                                | 施工令 §4.3⑩ 硬要求 ≤10fps；§9.6「耗电是隐形差评源」       |

动效曲线的纯函数全部有单测（`animation.test.ts`，27 项），
其中几条是**踩过坑之后写的回归**：

```
✓ ★ 眨眼的起点与终点必须是完全睁开的（旧实现让眼睛几乎永远闭着）
✓ ★ 眨眼过程中"接近闭合"的时间占比必须很小
✓ ★ 非对称：前半段比后半段涨得快（"被按下去又弹回来"的重量感）
✓ 耳朵相位滞后于身体——同相位会读成"整块图在转"
✓ 耳朵摆幅大于身体（带动关系才看得出来）
✓ 尾巴摆幅明显大于耳朵
✓ ★ 偏移量永远不超过上限 —— 瞳孔不能跑出眼白
```

> `bounceEnvelope` 那条第一次写错了：我用的 `sin(πp)^k` 关于峰值是**对称**的，
> 虽然"看起来"是非线性曲线，其实仍是对称的。是这条断言把它抓出来的。

### 9.3 图标与宠物同形

图标由 `pnpm icons` 程序化生成，并与宠物本体共用几何与配色。
过程中修掉两个真问题：

1. **防漂移自检是假的**：核对用的正则写成 `[^}]*` 会跨过形状边界，
   于是 `tailTip.cx` 实际匹配到文件里第一个 `cx`（body 的），
   核对永远通过却没在核对它以为在核对的东西。

   确认它以退出码 1 失败并打印出具体字段。
2. **图标里的耳朵原本是圆的**，与本体（尖耳）不同形，托盘图标像另一个角色。
   改成**采样与本体相同的贝塞尔曲线**做点在多边形内判定；
   用直线多边形近似的版本在小尺寸下耳朵是方的（试过）。

## 证据 4 补充 · 视线跟随（眼睛跟着光标转）

这不是施工令 M1 的原始要求，是重做外观时加上的**签名元素**：
"它注意到我了"那一刻的来源。

它有一个很隐蔽的失效方式：如果主进程只在**穿透路由翻转**时才推状态，
那么宠物在光标进入轮廓的那一刻看一眼、之后眼睛就冻住了——看起来像卡住。
**这个 bug 是加完视线跟随之后真的引入过的**，修法见下。

验证用**真的移动光标**（Win32 `SetCursorPos`）+ CDP 读回舞台的 gaze 向量。
判据不是"有没有偏移"（那可能是个常驻偏移），而是"**换方向后偏移跟着换**"：

```
  视线探针「左下」→ gaze = (-0.96, 1.03)
  视线探针「右下」→ gaze = (0.96, 1.03)
  视线探针「正上」→ gaze = (0, -0.89)
✅ ★ 视线随光标左右改变（左下的 gaze.x < 右下的 gaze.x）
✅ ★ 视线随光标上下改变（正上的 gaze.y < 左下的 gaze.y）
```

`gaze.x` 随光标左右**翻转符号**，`gaze.y` 随上下变化——眼睛确实在跟。

**修掉的 bug**：`#tickCursor` 里的 `#onStateChanged()` 原本挂在
"穿透路由翻转"那个分支下面，而路由只在跨过轮廓时才翻转。
后果：光标进入轮廓那一刻推一次状态、宠物看一眼，之后在轮廓内怎么移动都不推——
**眼睛冻住**。修法是把"路由翻转"与"光标位置变化"拆成两个独立条件。

代价：光标在宠物附近时 IPC 约每 80ms 一次（≈12 次/秒）。
可接受，因为只在光标接近窗口时才有值（远离时为 `null`，前后相等即不广播），
且 payload 极小。
